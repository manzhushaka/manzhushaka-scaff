# 菜单管理双栏结构设计

## 1. 背景

当前系统管理里的菜单管理页面仍然采用单表格平铺展示。虽然菜单数据本身存在 `parentId` 层级关系，后端也已经提供了菜单树接口，但页面没有把“目录 -> 菜单 -> 按钮”的结构直观展示出来，带来几个问题：

- 菜单层级阅读成本高，很难快速判断一个按钮归属到哪个菜单。
- 新增、编辑菜单时，用户需要额外在脑中维护结构关系。
- 当菜单数量增长后，单表格会越来越像“字段清单”，而不是“结构管理器”。

这次改造的目标，是把菜单管理页调整为更适合层级管理的双栏布局。

## 2. 目标与边界

### 2.1 目标

- 左侧展示完整菜单结构树，默认可直接看清目录、菜单、按钮之间的父子关系。
- 右侧展示当前选中节点的详情信息，减少在一行表格里堆叠过多字段。
- 保留现有新增、编辑、删除能力，不引入新的接口依赖和新的前端框架。
- 搜索仍然保留，但主要作用于左侧结构树的过滤与定位。

### 2.2 本期边界

- 本期优先改造 `ui-admin/src/views/system/menus.vue` 及其直接依赖。
- 本期尽量复用现有 `systemApi.listMenus`、`systemApi.getMenu`、`systemApi.listMenuOptions` 等接口。
- 本期不重做菜单表单结构，只在现有弹窗基础上继续复用。

### 2.3 非目标

- 不在本期引入拖拽排序、树节点拖放或批量操作。
- 不新增后端菜单领域能力，除非实现中发现前端无法复用现有接口。
- 不把菜单页改造成复杂的低代码配置器。

## 3. 核心方案

### 3.1 总体布局

页面保留顶部工具栏，主体改为左右双栏：

- 左侧为“菜单结构树”卡片。
- 右侧为“菜单详情”卡片。

结构上更接近“浏览 + 详情”的工作台，而不是传统数据表管理页。

### 3.2 左侧菜单结构树

左侧树负责承载层级感和主要导航能力：

- 默认展开全部节点。
- 节点直接展示菜单名称，并通过标签区分 `DIR`、`MENU`、`BUTTON`。
- 选中节点后，高亮当前项，并驱动右侧详情刷新。
- 节点区域提供轻量操作入口，例如“新增子菜单”“编辑”“删除”。

树节点的数据来源优先复用现有 `listMenus` 返回的平铺数据，在前端按 `parentId` 组装为树。这样可以避免额外依赖新接口格式，同时保持搜索参数兼容现有实现。

### 3.3 右侧菜单详情

右侧详情卡片用于展示当前选中节点的上下文信息，建议按信息块分组：

- 基础信息：菜单名称、菜单类型、上级菜单、排序、状态。
- 路由信息：路由地址、路由名称、组件路径、缓存策略。
- 权限信息：权限标识、显示状态。

右侧不再承载整页列表职责，重点是帮助用户确认“我当前正在编辑哪一个节点，它属于哪里，配置是什么”。

### 3.4 顶部工具栏

顶部仍保留：

- 菜单名称搜索框。
- “新增菜单”按钮。

其中：

- “新增菜单”默认创建根级菜单。
- 搜索后左侧结构树只展示命中的节点及其必要祖先路径，确保既能过滤又不丢层级上下文。

## 4. 交互设计

### 4.1 默认进入页面

- 页面加载后请求菜单列表。
- 前端将平铺菜单组装成树。
- 默认选中第一个根节点；如果没有根节点，则选中第一条可用节点。
- 右侧详情展示默认选中节点的信息。

### 4.2 搜索

- 搜索关键词仍使用菜单名称字段。
- 当存在关键词时，树结构进行过滤，但保留命中节点的父级链路。
- 如果当前选中节点在过滤后不可见，则自动切换到过滤结果中的第一个节点。
- 如果没有任何结果，左侧显示空状态，右侧显示“请选择菜单”或“暂无匹配结果”。

### 4.3 选择节点

- 点击左侧任意节点，右侧立即刷新详情。
- 同一个节点再次点击不触发额外请求。
- 详情展示基于当前列表数据即可完成，不强制每次选中都重新请求详情接口。

### 4.4 新增、编辑、删除

- 新增根菜单：使用顶部按钮，打开现有弹窗。
- 新增子菜单：使用左侧节点上的“新增子菜单”，自动带入 `parentId`。
- 编辑：可从左侧节点操作进入，也可保留右侧详情中的主操作按钮。
- 删除：可从左侧节点操作进入，删除成功后自动刷新树，并重新选中一个可用节点。

### 4.5 空状态与异常状态

- 无菜单数据时，左侧展示空状态，右侧展示引导文案。
- 搜索无结果时，左侧展示“暂无匹配菜单”。
- 删除当前选中节点后，优先选中同级下一个节点；若不存在，则回退到同级前一个或父节点。

## 5. 数据与代码落点

### 5.1 前端数据组织

建议在菜单页配套新增一个支持文件，例如 `menus-support.ts`，用于承载以下纯函数：

- 将平铺 `MenuVO[]` 组装成树结构。
- 基于关键词过滤树，同时保留祖先链。
- 计算默认选中节点。
- 将节点映射成右侧详情展示结构。

这样可以把树结构规则从页面组件中抽离出来，便于单元测试，也避免 `menus.vue` 再次膨胀。

### 5.2 接口复用策略

优先复用现有接口：

- `systemApi.listMenus`：菜单列表加载与搜索。
- `systemApi.listMenuOptions`：菜单表单上级菜单下拉。
- `systemApi.getMenu`：编辑时拉取完整详情。
- `systemApi.createMenu / updateMenu / deleteMenu`：沿用现有增删改链路。

本期不要求强依赖 `/system/menus/tree`，因为现有平铺列表已经足够组装左侧树，并且更方便兼容搜索行为。

## 6. 风险与取舍

### 6.1 为什么不直接用树表格

树表格改动最小，但它本质上仍然是“列表页”。菜单管理更关注结构关系和上下文，因此双栏在阅读体验上更自然，也更符合当前诉求里的“体现层级关系”。

### 6.2 为什么优先在前端组装树

后端虽然已有树接口，但当前页面已经基于平铺列表工作。前端组装树可以减少接口切换带来的不确定性，并保留现有搜索参数与返回格式的一致性。

### 6.3 需要控制的复杂度

双栏方案比树表格更美观，但也更容易让页面状态变复杂。因此本期需要严格控制：

- 不同时引入多套编辑入口逻辑。
- 不在首版加入拖拽、批量操作等扩展能力。
- 将树构建、过滤和选中回退逻辑收敛到支持文件中。

## 7. 验证方案

### 7.1 单元测试

新增前端单测，至少覆盖：

- 平铺菜单正确组装为层级树。
- 搜索过滤时能保留命中节点的祖先链。
- 当前选中节点无效时，能回退到合理的默认节点。

### 7.2 构建验证

至少执行：

- `cd ui-admin && pnpm test:unit`
- `cd ui-admin && pnpm build`

如果实现过程中出现必须依赖浏览器确认的样式问题，再额外做页面打开检查。

## 8. 预期结果

改造完成后，菜单管理页应具备以下体验：

- 左侧一眼看到整棵菜单结构树。
- 右侧稳定展示当前节点的详细配置。
- 按钮归属关系不再埋在平铺表格里。
- 现有菜单新增、编辑、删除流程保持可用。
